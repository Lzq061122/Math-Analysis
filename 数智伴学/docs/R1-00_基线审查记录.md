## 4. 数据模型关系（两代并存）

| 表 | 粒度 | 与本轮接口的关系 |
|---|---|---|
| `answers` | 一条作答（含 `fingerprint`、`source`、`missing`） | 身份与版本的事实来源；**没有 version 列，`fingerprint` 就是版本** |
| `answer_reviews` | 一次 AI 分析（`provider/model/causes/raw/answer_fingerprint/mistake_id`） | **旧 AI 路径**，确认后生成 `mistakes` |
| `followups` + `followup_updates` | 旧追问（挂 `mistake_id`/`review_id`） | 旧路径，与新的 `answer_followups` 并存 |
| `answer_checks` | 一次教师核对（`progress × cause_state`、`answer_version`、`locate_status/source`、`cause_code/label`、`cause_history`、`teacher_note`） | 新路径主体；`answer_version` = 保存时的 `answers.fingerprint` |
| `answer_followups` | 一次追问记录（`answer_id + answer_version`、`question`、`source`、`answer_text`） | 新路径追问；不依赖是否已生成错题 |
| `mistakes` | 正式错题（由旧路径确认而来） | **与新路线的统计未统一** → R1-08 要求给出设计说明 |

关键判断：
1. `answer_checks` 只有索引 `idx_checks_answer`，**没有 `UNIQUE(answer_id, answer_version)`**；重复保存靠 `current_check()` 先查后写，并发下不防重。
2. 新路径的"当前结论"判定 = `answer_version == answers.fingerprint`，旧版本记录保留但不参与队列/统计（`current_check`、`records` 的 `WHERE` 都带此条件）。
3. `answer_followups.source` 目前只有 `preset` / `teacher` 两个取值，且 `preset` 的判定方式是"问句是否等于默认问句"（见 §5 R1-06）。

## 5. 逐项缺陷复现状态

### R1-01 合成证据污染真实作答 —— **已确认缺陷**

- `src/app/answer_check.py:154-159` `candidates_for(answer)` 只取 `answer["question_text"]` 交给 `demo_answers.preset_causes()`，**不校验 `answers.source`、`record_key`、学生步骤或版本**。
- 可达路径：`GET /api/classes/{id}/check/answers/{answer_id}` → `detail()`（`:399`）→ `:406 candidates = candidates_for(answer)[:MAX_CANDIDATES]` —— 对**真实作答也无条件调用**。
- 对比：同一文件的 `_demo_record()`（`:118-137`）对预置**定位**有严格守卫（`source == 合成演示` + `record_key` + `question_text` + `student_steps` 全等），说明作者知道该守卫，但候选路径漏了。
- 后果：真实作答只要题干文本与演示题目规范化后相同，就会拿到演示案例的候选错因与证据（含演示学生原话式证据），违反 PRD §4.1"分析以证据为基础"与规格 §3.1.3"只检索已审错因库"。

### R1-02 教师人工判断能力 —— **已确认缺陷**

- 库表无"判断依据"字段：`answer_checks` 只有 `teacher_note`（备注）与 `cause_code`/`cause_label`，**判断依据与备注不分列**。
- 无来源字段：无法区分"采纳候选"与"教师自行填写"，`cause_history` 只记 code/label/decided_at（`:534-538`）。
- 无"是否已加入通用错因库"标记（本轮也不建库，但来源标记是 R1 要求）。
- 人工填写路径本身存在（`cause_code`/`cause_label` 由请求体直传，`:496-499`），但**无候选时前端能否走到这里**属前端契约问题，需与 R1-03 一起定。

### R1-03 保存结果与接口状态 —— **已确认缺陷（两处）**

1. **静默纠正**：`src/app/answer_check.py:500-503`
   ```python
   if _force_undecided(answer, locate["status"]):
       cause_state = CAUSE_UNDECIDED
       cause_code = ""
       cause_label = ""
   ```
   教师提交"已判断 + 原因"时，若该作答被判为 correct / missing / out_of_scope 等，服务端**悄悄清空原因并返回 200 成功**，响应里没有说明被改过 —— 正是任务书"不得静默修改用户提交的判断后仍返回容易误解的成功信息"所指。
2. **返回体不足**：`:603-618` 只返回 `receipt{class_name, assignment_name, saved_at, status_line}`、`judgement`、`queue{next_answer_id, is_last, remaining, total}`。缺：作答 ID 与版本、数学核验结果、实际保存的错步、追问记录、当前批次名与"下一份作答"的完整身份。
3. 已有且合格的部分：`expected_version` 版本冲突返回 409（`:_483-490`、二次校验 `_524-529`）、写入在 `db.tx()` 单事务内（`:522`）、追问插入前做同问同答去重（`:578`）。

### R1-05 人工核对路径 —— **已确认缺陷（部分）**

### R1-06 追问记录与证据更新 —— **已确认缺陷（两处）**

1. **无条件去括号问句**：`src/app/answer_check.py:28`

   `_save` 在客户端没给问句时无条件兜底为它（`:516-517`），与错因、错步类型无关 —— 任务书点名的"移项错误也返回去括号问句"。合成演示有专属问句时走 `_default_question()`（`:170-177`），真实作答一律落到这条常量。
2. **来源靠问句判定**：`_followup_source()`（`:459`）

   真实作答被兜底成默认问句后，`answer_followups.source` 会被写成 `preset` —— 来源标签失真，且无法表达"未来已审资源库追问"。

**R1-06 结构性缺陷**：`_default_question(answer)` 的签名拿不到 `locate.status` / `cause_code` / `first_bad_text`，**结构上不可能按错因选句**；无「无资源」分支，永远有句子可显示。纯移项题 `2x+7=15` 也被问「你当时是怎么展开这个括号的？」。前端还有一份同样的兜底（`src/web/app.js:1737 CHECK_ASK_FALLBACK`、`:2066`）。落库的追问 `source="preset"`、`asked_at` 等于保存时刻（不是真实提问时间）。

**模型不可用时（任务书要求）——已满足，属于要保留的基础**：无环境变量时 `mode='mock'`/`MockProvider`；`equation_steps` 只用 `re`+`Fraction` 且头注明写不调用模型；`answer_check`/`stats`/`advice` grep 网络关键字命中 0；mock 下 `tutor`/`followup`/`answer_review` 各自 409 拒绝而不静默改模拟；`MockProvider` 没有 `chat_text`，不可能误走文字通道；分析失败仍落库不丢数据（`_failure_result:461`）。

**结论**：不满足「个体业务不触发外部模型请求」。当前形态是「默认关闭 + 每次手点 + 勾选同意」，不是隔离；每条生成路径都由服务端主动读业务库再外发，与规格 §5「业务环境只运行固定规则与人工流程，不发起个体化生成式请求」「AI 接口不读取学生记录」相反。
