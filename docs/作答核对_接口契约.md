## 1. 数据模型

### 1.1 新增表（`src/app/db.py`）

```sql
-- 一次「作答核对」的教师结论。与 answer_reviews（AI 候选错因）分开：
-- answer_reviews 是模型候选，answer_checks 是教师对这份作答的处理记录。
-- R1-02 / R1-03 增列见 §1.3（cause_source / basis_note / completion_state / invalidated_* …）。
CREATE TABLE IF NOT EXISTS answer_checks (
    id             INTEGER PRIMARY KEY,
    class_id       INTEGER NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
    student_id     INTEGER NOT NULL REFERENCES students(id) ON DELETE CASCADE,
    answer_id      INTEGER NOT NULL REFERENCES answers(id) ON DELETE CASCADE,
    batch          TEXT NOT NULL DEFAULT '',
    answer_version TEXT NOT NULL DEFAULT '',   -- 保存时的 answers.fingerprint；撤回后置空
    progress       TEXT NOT NULL DEFAULT 'checked',   -- checked | pending（pending 只出现在撤回行）
    cause_state    TEXT NOT NULL DEFAULT 'undecided', -- undecided | decided | not_applicable
    observed_step  TEXT NOT NULL DEFAULT '',   -- 观察到的错步（老师可改）
    first_bad_index INTEGER,                   -- 0 基，指向 lines 下标；只对 first_bad 有效
    locate_status  TEXT NOT NULL DEFAULT '',   -- 见 §2 status
    locate_source  TEXT NOT NULL DEFAULT '',   -- rule | preset | none
    contrast_note  TEXT NOT NULL DEFAULT '',
    cause_code     TEXT NOT NULL DEFAULT '',
    cause_label    TEXT NOT NULL DEFAULT '',
    cause_history  TEXT NOT NULL DEFAULT '[]', -- 改判/撤回历史（旧结论不再作为当前结论，但保留）
    teacher_note   TEXT NOT NULL DEFAULT '',
    created_by     INTEGER,
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL,
    decided_at     TEXT NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_checks_answer ON answer_checks(answer_id);
CREATE INDEX IF NOT EXISTS idx_checks_class  ON answer_checks(class_id, batch);
-- 同一份作答的同一版本只能有一条当前结论（A→B→A 不许堆行）；撤回行 answer_version 置空，不受限制。
CREATE UNIQUE INDEX IF NOT EXISTS idx_checks_answer_version
    ON answer_checks(answer_id, answer_version) WHERE answer_version <> '';

-- 当面追问的原话记录，挂在「作答 + 版本」上，不以已生成错题为前提。
CREATE TABLE IF NOT EXISTS answer_followups (
    id          INTEGER PRIMARY KEY,
    class_id    INTEGER NOT NULL REFERENCES classes(id) ON DELETE CASCADE,
    student_id  INTEGER NOT NULL REFERENCES students(id) ON DELETE CASCADE,
    answer_id   INTEGER NOT NULL REFERENCES answers(id) ON DELETE CASCADE,
    check_id    INTEGER REFERENCES answer_checks(id) ON DELETE SET NULL,
    answer_version TEXT NOT NULL DEFAULT '',
    question    TEXT NOT NULL DEFAULT '',
    source      TEXT NOT NULL DEFAULT 'preset',  -- preset | teacher | library（已审资源库）
    source_detail TEXT NOT NULL DEFAULT '',      -- 来源补充说明（R1-06 用）
    answer_text TEXT NOT NULL DEFAULT '',
    asked_at    TEXT NOT NULL DEFAULT '',
    answered_at TEXT NOT NULL DEFAULT '',
    invalidated_at TEXT NOT NULL DEFAULT '',     -- 失效标记（关键证据变化时置位）
    invalidated_reason TEXT NOT NULL DEFAULT '',
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_answer_followups_answer ON answer_followups(answer_id);
```

### 1.2 当前版本判定（不做存量刷新）

`answer_checks.answer_version` 与 `answers.fingerprint` 相等时才算「当前结论」。
重导导致 `fingerprint` 变化后，旧结论**自动退出**当前视图、队列与统计（查询时按版本过滤即可，不写任何清理逻辑），该作答自动回到「待核对」。历史上保留原记录，供追溯。

### 1.3 R1-02 / R1-03 增列与迁移（向后兼容）

| 列 | 用途 | 由谁写 |
|---|---|---|
| `cause_source` | 错因来源：`none` / `preset`（采纳候选）/ `teacher`（教师填写）/ `legacy`（历史行）。**`legacy` 的识别方式**：T4 之前（第一轮）写下的 `answer_checks` 行没有来源列，迁移时凡 `cause_code` 非空而 `cause_source` 为空的行都回填为 `legacy` —— 它表示「这条结论确实判过原因，但当时没记来源」，不能读成 `none`（`none` 是「从未判断」）。前端与统计按同一张标签表显示「历史记录（来源未记录）」 | 保存 / 迁移回填 |
| `basis_note` | 判断依据（与 `teacher_note` 备注**分列**，R1-02） | 保存 |
| `change_reason` | 最近一次改判/撤回理由 | 保存 |
| `completion_state` / `failed_line_index` / `verification_scope` | T3 的 ④ 完成情况与核验范围快照（可查询、可统计） | 保存 |
| `manual_state` / `manual_reason` | T3 的 ⑤ 人工处理状态（`none`/`referred`/`need_steps` + 原因码） | 保存 |
| `locate_detail` | ③④⑤+核验范围四组结构的 JSON 快照（历史结论不受规则引擎改版影响） | 保存 |
| `decided_by` | 做出「教师已判断」的操作人 | 保存 |
| `invalidated_at` / `invalidated_reason` / `invalidated_by` | 撤回痕：谁在何时为何撤回（行保留、`answer_version` 置空） | 撤回 |
| `answer_followups.source_detail` / `invalidated_at` / `invalidated_reason` | 追问来源补充与失效标记（R1-06 用） | 保存 / 证据更新 |

**R1-05 / R1-06 增列**（同一套迁移，同样只加列、不动旧行）：

| 列 | 用途 | 由谁写 |
|---|---|---|
| `answer_checks.verify_source` | 这条结论的**证据来源**：`''` / `rule`（规则定位）/ `preset`（合成演示预置定位）/ `manual`（规则判不了或规则给不出这个错步，由教师人工核验）。人工结果与规则结果**分列**，统计与记录据此区分（§3.9） | 保存 |
| `answer_checks.teacher_error_text` | 教师人工记录的数学错误原文（与规则填的 `observed_step` 分列，规则给的错步仍留历史） | 保存 |
| `answer_checks.teacher_verified_at` / `teacher_verified_by` | 人工核验留痕：谁在什么时候核验的 | 保存 |
| `answer_followups.evidence_snapshot` | 这条追问是「拿哪份证据」问的：`{answer_version, locate_status, locate_source, verify_source, first_bad_index, observed_step, cause_state, cause_code}`。关键证据一变，旧确认据此失效（§3.9） | 保存 |

迁移（`ensure_answer_check_schema`）：只读检查（表 + 索引 + 上述新列都在才算就绪）→ 一致性备份 → `BEGIN IMMEDIATE` → **先建表（两张表）→ 再逐列 `ALTER TABLE ADD COLUMN`（已有列跳过）→ `cause_source` 历史行回填 `legacy` → 合并重复 `(answer_id, answer_version)` 行（保留 id 最大者，被合并行的结论写进 `cause_history`）→ 最后建索引（含唯一部分索引）** → `COMMIT` → 复核。失败抛 `MigrationError`，原库不动。

> **T6 修复的旧库迁移 bug**：这个顺序原来写成「建 `answer_checks` → 补两张表的列 → 建 `answer_followups`」，于是 1.7.x 旧库（两张表都不存在）在补 `answer_followups` 的列时会抛 `no such table: answer_followups`，整次升级失败（基线 ee95789 同样失败，非 R1 引入）。现在按上面的顺序执行；150 套件 17.13–17.17 用 `tests/fixtures/legacy160/app.db` 锁死这条：升级成功且数据不丢，把「先建表」改回旧顺序则必须重新抛 `MigrationError`（反向自证）。

**如何回滚**：迁移前都有 `app.db.bak-<时间戳>-<随机>` 一致性备份，覆盖回去即恢复旧结构；只想撤唯一索引时删掉 `idx_checks_answer_version` 即可（其余都是加列，不影响旧读写）。旧库补上的新列取空值：`verify_source=''` 读作「未记录来源」，`evidence_snapshot='{}'` 读作「这条追问没有证据快照」——历史追问因此**不会**被误判成「证据已变」，也不会被误判成「已确认」。

## 2. 确定性错步定位（`src/app/equation_steps.py`，新文件）

纯函数、离线、无随机、无网络、无第三方库（只用 `re` 与标准库）。

```python
def locate(question_text, standard_solution, student_steps, missing=False, missing_reason="") -> dict
```

返回（**键名固定**，前后端与测试都按这个读）：

```python
{
  "status": "correct" | "first_bad" | "missing_steps" | "missing" | "out_of_scope",
  "source": "rule" | "none",
  "first_bad_index": 1 | None,        # 0 基，指向 "lines" 下标
  "first_bad_text": "3x-2=12" | None,
  "underline": {"start": 3, "end": 5} | None,   # 相对 first_bad_text 的字符偏移
  "hint_text": "-2" | None,           # 被划线的那一段原文（逐字取自 first_bad_text）
  "contrast": {
      "expected": "3x-6" | None,      # 上一步本应得到的等价形式；算不出就 None
      "actual": "-2" | None,
      "note": "展开后应为 3x-6；括号外的 3 也要乘以 -2。"   # 固定句，见下
  },
  "reason_note": "",                  # 不推断原因的说明，见下
  "manual_note": "",                  # status 为 out_of_scope / missing_steps 时给老师的话
  "lines": [{"text": "3(x-2)=12", "role": "given", "bad": False},
            {"text": "3x-2=12",  "role": "student", "bad": True}]
}
```

**status 语义（验收即按此判定）**

| status | 触发 | 必须保证 |
| --- | --- | --- |
| `missing` | `missing=True` | 不标错步、不算错、不猜原因；`reason_note` 说明缺测 |
| `missing_steps` | 学生正文只有结论行（如只有 `x=1`） | 只提示「缺少步骤」，`first_bad_index=None`，不猜错在哪一行 |
| `correct` | 题干到学生各行全程等价 | 不标错；`first_bad_index=None` |
| `first_bad` | 相邻两行解集不同 | 给出**首个**不等的某一行，含 `underline` + `hint_text` + `contrast` |
| `out_of_scope` | 非一元一次方程、含无法解析的符号或运算 | 不判、不标错，`manual_note` 写「已转人工」，原步骤照常完整显示 |

**判定规则（限定题型：一元一次方程）**
1. 一行里只能出现一个未知数（`x` 或 `y`），可含整数、小数、`/` 分数、括号、正负号、等号两侧。
2. 把每行化到 `Ax + B = Cx + D`（`A,B,C,D` 为有理数，用 `fractions.Fraction`，避免浮点误差）。
3. 两行「解集相同」⇔ `(A-C, B-D)` 与另一行的 `(A'-C', B'-D')` 成比例（含 0 向量、无解、全体实数三种退化情形）。用有理数交叉相乘判等，不用 `float`。
4. 从题干那行起，逐个与下一行比较，**第一个不等价**的后一行即 `first_bad_index`。比较到学生最后一行结束。
5. 全角/半角（`－`、`×`、`（）`、`﹣`）、空格、`*`、省略乘号都要能吃下；`3(x−2)` 与 `3 * (x-2)` 视为同一形式。
6. `underline`：把 `first_bad_text` 与「上一步按规则得到的形式」做逐项对比，取第一处数值不同的常量项（如 `-2` vs `-6`）；取不到就退回整行（`start=0,end=len`）。
7. `hint_text` 必须逐字出现在 `first_bad_text` 里（测试会断言 `hint_text in first_bad_text`）。
8. `contrast.note` 只用两种句式的模板：
   - 上一步是 `k(a±b)` 单括号形式 → `展开后应为 {expected}；括号外的 {k} 也要乘以 {b}。`
   - 其它情形 → `这两行不等价：上一行是 {prev_raw}，学生这一行是 {bad_raw}。`
   - 两者都算不出 → `这两行的解集不同；具体变形请对照标准解法的对应步骤。`
   - **`contrast.expected` / `contrast.actual` 与 note 里的两段原文必须是「同一种形态」，且逐字取自作答原文**（lead 2026-11-24 补充裁定，见 §2.1）。
9. `reason_note` 固定为一句：`这里只记录观察到的不等价，不推断学生为什么这样写。`

**禁止事项**：不输出任何「学生可能是……」「因为学生……」式的推断；`status` 与 `first_bad_index` 在任何调用顺序、任何进程重启后完全一致（确定性测试两条：同进程两次调用一致、跨进程一致）。

**预置案例**：`equation_steps.locate` 只走 `source="rule"`。合成演示数据若用预置错步（案例 A），由 `demo_answers.py` 直接给出定位结果，`source="preset"`，界面必须显示「预置演示 · 不代表已实现通用定位」。

### 2.1 lead 补充裁定（2026-11-24，T1 抽查发现）

**问题实录**：案例 B（`5x-3=2x+6` → `5x-2x=6-3` → `x=1`）实际输出
`这两行不等价：上一步等价形式是 5x-3=2x+6，学生这一行是 3x=3。`
其中 `3x=3` 是 `5x-2x=6-3` 的**化简结果**，学生那一行并不是这么写的。对照的两端一个是原文、一个是化简式，形态不一致，会把「学生写了什么」说错——这正是评审禁止的「替学生补写」。

**裁定（三条都要满足）**：
1. 通用句式改为 `这两行不等价：上一行是 {prev_raw}，学生这一行是 {bad_raw}。`，两段都**逐字取自作答原文**（`{bad_raw}` 必须等于 `first_bad_text`）。
2. `contrast.expected` / `contrast.actual` 若给化简形态，必须在字段名之外用文字标明（例如 note 里写「化简后分别是 3x=9 与 3x=3」），不得让化简式冒充学生的原文；`contrast.actual` **必须**满足「等于 `first_bad_text`」或「在 note 中被明确标注为化简后」。
3. 案例 A 的单括号模板（`展开后应为 3x-6；括号外的 3 也要乘以 -2。`）保持不变——它是算术对照，不是说学生写了 `3x-6`。

**回归要求**：改完后 `hint_text in first_bad_text`、`status`、`first_bad_index` 三条既有不变量不得变化；案例 A 的 `underline`/`hint_text`/`expected` 保持原值。

**第 4 条（同日补，见 §4.2 的 R-07 裁定）**：`contrast.actual` 必须与 `hint_text` 逐字相等，两者都逐字取自 `first_bad_text`；全角 `－`（U+FF0D）、小连字符 `﹣`（U+FE63）、数学减号 `−`（U+2212）一律保留学生写法，不得规范化成 ASCII `-`。任何规范化只允许出现在 `contrast.expected` 一侧，且必须能被上一行原文解释。
> 实测（24 日 15:26）：四种减号写法下 `hint_text == contrast.actual == first_bad_text[start:end]` 全部成立，案例 A 半角输出零变化。

## 3. HTTP 接口（`src/app/api.py` + `ROUTES`）

统一前缀 `/api/classes/{id}/check`，全部 `need_auth=True`，全部经 `owned_class(ctx.db, ctx.user, id)` 做班级归属校验。
错误体沿用仓库约定：`{"error": "...", "code": "..."}`（见 `ApiError`）。

### 3.1 `GET /api/classes/{id}/check/overview?batch=`

```json
{
  "state": "no_answers" | "has_pending" | "all_checked",
  "assignment": {"batch": "9月第2次作业", "name": "9月第2次作业", "total": 4, "pending": 2,
                 "checked": 2, "missing": 1},
  "assignments": [{"batch": "...", "name": "...", "total": 4, "pending": 2, "checked": 2}],
  "next": {"answer_id": 12, "student_label": "学生 A", "question_no": "1",
           "headline": "去括号：是规则没掌握，还是这次漏写？",
           "notice": "定位结论的一句话说明（非 first_bad 时非空）", "locate_status": "first_bad"},
  "counts": {"answers": 4, "synthetic_answers": 0, "checks_current": 2,
             "undecided_cause": 1, "not_applicable_cause": 1}
}
```

- `state`：班级一条作答都没有 → `no_answers`（界面文案「尚未导入作答」）；当前作业 `pending>0` → `has_pending`；`pending==0` 且 `total>0` → `all_checked`（界面文案「本次作业已核对完」）。
- 不传 `batch` 时，当前作业 = `MAX(imported_at)` 那条作答所属 batch；并列时取 id 较大者。传了就按传入的 batch。
- `next`：与「查看下一份」**同一队列**——该 batch 内、当前版本无有效 check 的作答，按 `id ASC` 第一条。
- `next.headline`：固定模板，取定位结果：`first_bad` → `去括号：是规则没掌握，还是这次漏写？`（本轮固定文案，按 `locate_status` 选模板，不生成自由文本）。
- `assignment.missing`：该 batch 里 `answers.missing=1` 的条数。

- `queue.position` / `is_last` 基于 §3.1 的同一队列（已保存的不再计入 `pending`；`position` 在保存前后都按「本份在队列中的序号」算）。

规则（R1-02 / R1-03 修订，全部在**任何写入之前**校验）：

1. `expected_version != answers.fingerprint` → 409 `version_conflict`，不写库。
2. `progress=pending`（撤回）：要求这份**当前版本**已有结论，否则 400 `nothing_to_retract`；撤回把该行的 `answer_version` 置空（`invalidated_at/_reason/_by` 记录谁在何时为何撤回），本份立即回到「待核对」队列；行本身与 `cause_history` 全部保留，可追溯。撤回后再次保存会新建当前版本结论，历史里能看到 `retract` 事件与原结论。
3. 原因轴三态（**契约变更**，替代旧的"强制压回 undecided"）：
   - `first_bad`（有首处错步）：`undecided`（真欠账）或 `decided`；
   - `out_of_scope`（规则判不了）：`not_applicable`（默认，不欠账）或 `decided`（教师人工判断）；
   - `correct` / `missing_steps` / 缺测：只能 `not_applicable`；提交 `decided` → 400 `cause_not_applicable`。
   - 老师没判原因、而这本题既不是 `first_bad` 也不是"可判可不判"时，服务端把它记为 `not_applicable` 并在 `adjustments` 里写明原因——**这是唯一一处服务端补状态，且必须回给前端**。
   - **只有 `applicability=optional`（out_of_scope）才强制判断依据（T11 口径）**：这一档规则给不出错步，行里除了老师写的原因说明什么都没有，所以 `decided` 必须带 `basis_note`（本次填的或上一次留下的都算），否则 400 `basis_required`、一条不写。`applicability=required`（first_bad）**不强制依据**——那时 `observed_step` 默认已落错步原文，客观证据在行里，强制依据会把 A5「保存错步，原因待判断」的快路径卡住；`forbidden` 三档更轮不到依据问题（直接 400 `cause_not_applicable`）。
4. `cause_state=decided` 必须带 `cause_code` 与 `cause_label`，否则 400 `cause_required`；`undecided`/`not_applicable` 带 code/label → 400 `cause_state_mismatch`（旧实现原样落库，属静默纠正）。
5. `cause_source=preset` 而 `cause_code` 不属于本条候选 → 400 `cause_not_in_candidates`。
6. `first_bad_index`：只在 `first_bad` 时允许；`1 ≤ index < len(lines)`（第 0 行是题干），否则 400 `bad_index`（旧实现对非 first_bad 静默丢弃、对 0 与末行照收）。
7. 任何文本超限 → 400 `text_too_long`（附字段名与上限），**不再静默截断**。
8. `progress` 取值非法 → 400 `bad_progress`；`cause_source` 非法 → 400 `bad_cause_source`。
9. 改判/说明变化 → 把旧结论整条推进 `cause_history`（`action="revise"`，含 code/label/state/source/note/basis/decided_at/by/at）；`clear_notes` 与撤回同样留痕。
10. 保存失败（异常、磁盘、并发）→ 500 `save_failed`，**一条都不写**，前端必须留在当前页并保留全部输入。
11. 同一 `(answer_id, answer_version)` 唯一（部分唯一索引 `idx_checks_answer_version`），A→B→A 反复提交只会更新同一行；撤回行 `answer_version` 置空，因此不受唯一约束限制。
12. **人工核验（R1-05 新增）**：`observed_step` 由老师自己写、且与规则给的首处错步逐字不同 → 这次结论的 `verify_source=manual`，同时把这段文字写进 `teacher_error_text`（与规则给的结果**分列**），并记 `teacher_verified_at/by`；`out_of_scope` 这类规则判不了的作答形成了原因判断（`decided`）时同样记 `manual`。`manual` 必须带 `basis_note`（本次填的或上一次留下的都算）→ 否则 400 `basis_required`，一条不写。
13. **追问来源三值（R1-06 新增，写入规则）**：
    - `preset`：问句逐字等于服务端为**本条作答**给出的建议问句（合成演示＝五项全匹配的预置记录；真实作答＝按本条错步生成的建议句）；
    - `library`：问句逐字命中已审资源库（B2 预留，本轮库为空）；
    - `teacher`：其余一切（老师自拟，或把建议问句改过哪怕一个字）。
    细分来源写 `answer_followups.source_detail`（`demo_record` / `rule:term_move` / `rule:bracket_expand` / `rule:rewrite` / `teacher` / `library:<id>`）。**判据不再是「与一句写死的常量相等」**——移项题因此不会被标成去括号问句，来源标签也不会失真。
14. **追问证据失效（R1-06 新增）**：写入追问时把当时的结论快照存进 `evidence_snapshot`；同一份作答同一版本上，凡快照与本次结论不一致的旧追问一律标 `invalidated_at` + `invalidated_reason`（`evidence_changed：<差异说明>`），原有原话不删。撤回结论 → `conclusion_retracted`；补录/校正内容（新版本）→ `answer_updated`。详情里的 `followup.recorded` 只在「当前版本 + 未失效 + 快照与当前结论一致」时为 `true`。

1. `expected_version` 必填且必须等于当前 `answers.fingerprint`，否则 409 `version_conflict`。
2. 只许改题面 / 标准解 / 学生步骤 / 单元 / 作答日期 / 缺测 / 缺测原因；**身份字段（学生、题号、记录编号、批次）不许改**。
3. 文本超限 → 400 `text_too_long`；日期格式不对 → 400 `bad_date`；`missing` 只能是「是/否」→ 否则 400 `bad_missing`；缺测却有步骤、或非缺测却没有步骤 → 400 `bad_missing`；内容与当前值完全一样 → 400 `nothing_to_update`。
4. 内容指纹按新文字重算：`answers.fingerprint` 变了 → 旧 `answer_checks` 自动成为旧版本（`judgement.stale=true`），本份回到待核对队列；响应里的 `locate` / `candidates` / `followup` 全部按**新内容**重新分析（`reanalysed=true`）。
5. 旧版本上的追问按 `answer_updated` 标记失效（原话不删，见 §3.9）。
6. 合成演示作答 → 409 `demo_readonly`：它是「五项全匹配」预置的基线，改了内容预置定位与候选就会失效；演示数据请用「重置合成数据」恢复。
7. 失败的补录（409/400 任一）不写入任何内容、不新增版本、不动指纹。

### 3.5 合成演示数据（A7）

```json
POST /api/classes/{id}/check/demo/seed   {} → {"ok": true, "seeded": {"answers": 4, "synthetic": true}, "class_id": 3}
POST /api/classes/{id}/check/demo/reset  {} → {"ok": true, "deleted": {"answers": 4, "followups": 1}, "kept": {"imported_answers": 2}}
```

只增删 `answers.source='合成演示'` 的作答及其 `answer_checks`/`answer_followups`/`answer_reviews`；**真实导入的作答一条都不动**，`kept.imported_answers` 用数字证明。两个接口都不联网、不读文件。

### 3.6 班级统计（A3 口径，`src/app/stats.py`）

在 `GET /api/classes/{id}` 与 `GET /api/classes/{id}/stats` 的返回里新增 `answer_check` 块（不改动既有字段含义）：

```json
{"answer_check": {"batch": "...", "expected": 10, "valid": 8, "missing": 1, "pending": 1,
                  "checked": 7, "original_errors": 5, "cause_decided": 2,
                  "cause_not_applicable": 3, "manual_verified": 1,
                  "basis": "原题错误数按已保存错步计；原因判断数单独统计，两者口径不同"}}
```

- `expected` 应交 = 该 batch 作答数；`valid` = `missing=0`；`missing` = `missing=1`；`pending` = 当前版本无 check；`checked` = 有当前 check。
- `original_errors` 只数「当前 check 且定位为 first_bad」；`cause_decided` 数 `cause_state=decided`。
- 缺测与正确作答**不计入** `original_errors`。
- **R1-08 / T6 收口（这三条是硬口径，评审逐条核对）**：
  1. **合成演示数据一律不进本块**：所有计数都带 `a.source<>'合成演示'`。这条现在是**唯一**防线——原先两个「写入时把演示行挪回演示批次」的库级触发器已删除（见 §5.3），所以统计侧必须显式过滤；实测「把演示行直接写进真实批次」时 `expected` / `checked` / `original_errors` 全都不变（150 套件 17.5–17.7）。
  2. **当前结论只有一个判据**：`c.answer_version = a.fingerprint`。撤回（版本置空）或重导（指纹变化）后旧 check 自动退出 `checked` / `original_errors` / `cause_*` / `manual_verified`，只是历史行仍留在库里（150 套件 17.11/17.12）。
  3. **两档新增计数与总览同源**：`cause_not_applicable`（无需判断）与 `manual_verified`（人工核验）分别等于 `overview.counts.not_applicable_cause` 与 `overview.counts.manual_verified`；`JOIN answers a ON a.id=c.answer_id AND a.class_id=c.class_id`，`answers.class_id` 被改动也不会跨班串味（150 套件 17.8–17.10）。

### 3.7 实现口径补充（T1 交付后回写，lead 已逐条核对并接受）

backend 在契约未写明处做了 7 个选择，lead 判定均可接受，记录在此避免复审时被当成偏离：

1. `stale` 仅在「没有当前版本 check、但存在旧版本 check」时为 `true`；已有当前版本 check 时旧记录只进历史，不永久提示失效。→ 与 §1.2「按版本过滤」一致，且避免老师重存后仍被警告。
2. 保存是**更新同一 `(answer_id, answer_version)` 的 check 行**；改判时旧原因进 `cause_history`，不堆叠重复行。
3. `queue.next_answer_id` 取保存后队列中 **id 最小**的待核对项（乱序核对不会误报收尾）；`queue.total` 把刚保存那份算回来。
4. 传入的 `batch` 在本班没有任何作答时 `state="no_answers"`（不显示「已核对完」）；`records` 不传 `batch` 时列全班当前版本 check。

### 3.8 R1-02 / R1-03 落地口径（本轮修订，评审逐条核对用）

### 3.9 R1-05 / R1-06 落地口径（本轮修订，评审逐条核对用）

1. **人工核验轴与规则结果分列存**（R1-05）：`answer_checks.verify_source` 记这条结论的证据来源（`rule` / `preset` / `manual`），`teacher_error_text` 记教师人工写下的错步；规则给的 `observed_step` 与 `locate_status` 原样保留，两者不互相覆盖。判 `manual` 的条件只有两条：① 老师写的错步与规则给的首处错步逐字不同；② 规则判不了（`out_of_scope`）却形成了原因判断。
2. **人工核验必须留依据**（R1-05「不得绕过证据与审核门禁」）：`manual` 而 `basis_note` 为空 → 400 `basis_required`，一条不写。省略或空串的 `basis_note` / `teacher_note` / `observed_step` 一律按「这次不改」处理（沿用上一次），只有 `clear_notes=true` 才清空——否则「只改错步」的一次保存会把上次写下的核验依据静默清空（本次已修：旧代码只判了 `None`，与本节承诺不符）。
3. **单条补录/校正**（R1-05）：见 §3.4.1。指纹一变，旧结论自动成为旧版本（`stale`），响应里直接给出按新内容重新分析的 `locate`；旧版本上的追问按 `answer_updated` 失效。
4. **问句由本条错步决定**（R1-06）：见 §3.2 的 `followup.suggestion` 四条优先级。移项题问的是移项（逐字引用这两行原文与换边的那一项），括号题才问括号；正确 / 缺测 / 缺少步骤 / 超范围一律 `available=false` + 「暂无适用追问」，并说明为什么暂无。
5. **来源三值写入规则**（R1-06）：`preset`（逐字等于系统为本题给出的建议问句）/ `library`（逐字命中已审资源库，B2 预留）/ `teacher`（其余）；细分来源在 `source_detail`。判据不是「等于一句写死的常量」。
6. **证据更新即失效**（R1-06）：`answer_followups.evidence_snapshot` 记证据；写新结论时把快照不一致的旧追问标 `evidence_changed：<差异说明>`，撤回标 `conclusion_retracted`，补录标 `answer_updated`；原话不删，`followup.history` 里可读。详情 `recorded` 与 `needs_review` 按「当前版本 + 未失效 + 快照一致」计算，前端据此显示「上一次记录的学生回答已不再是当前证据」。

### 3.10 T11 落地口径（「证据不足不得直接判错」的收口，评审逐条核对用）

1. **闸门只对 `applicability=optional` 生效**：`out_of_scope` + `cause_state=decided` + 有效 `basis_note` 为空 → 400 `basis_required`，一条不写。实现位置是 `_require_manual_evidence()`（`out_of_scope` 上形成原因判断即记为 `verify_source=manual`，因此与 R1-05 的人工核验共用同一道闸门，**不另写一套校验**）。
2. **有效依据的口径**：本次填的非空 `basis_note`，或同一条当前版本上此前已留下的 `basis_note`；`clear_notes=true` 视为清空、直接拒绝。省略/空串一律「这次不改」，不会把上次的依据静默清掉。
3. **`first_bad`（required）不强制依据**：`observed_step` 默认即错步原文，客观证据在行里；A5 的「保存错步，原因待判断」快路径因此不受影响（`first_bad + decided + 无依据` 仍 200，`verify_source=rule`）。
4. **`forbidden`（correct / 缺测 / 缺少步骤）**：照旧直接 400 `cause_not_applicable`，与依据无关。
5. **不做的更严口径（R2 遗留）**：「所有 `cause_source=teacher` 的判断一律强制依据」会破 150 套件 6.1–6.6 / 10.1–10.2 与 UI 13.6 / 13.14 的既有断言，属第二轮契约变更，本轮不做。
6. **前端最小适配**：`applicability=optional` 且当前未记成「无需判断」时，「判断依据」标签写明「本题规则判不了：人工改判原因时必填」并附一句提示（`.basis-hint`），满足必填即可保存；记成「无需判断」后提示消失（不要求依据）。
7. **反向自证**：150 套件 11b.1 断言该 400，12.12–12.14 用变异体把闸门摘掉后同一条调用不再报错、真实实现仍抛 `basis_required`——证明这条断言不是恒真。

### 4.2 lead 裁定（2026-11-24，T5 评审后回写；**修正上面的 ⑤ 与 §4 的 A1**）

T5 评审提出 R-04 / R-06 / R-07 三条需要我裁定的偏离。逐条裁定如下，**与本文件其它部分冲突时以本节为准**。

**R-04（medium）｜`decided` 状态下主按钮的语义与文案**

事实：当这份作答已保存过「教师已判断」的原因时，主按钮（文案仍是「保存错步，原因待判断」）实际发出 `cause_state='decided'`，等于按钮在撒谎；而且 `decided` 之后界面没有任何回到「原因待判断」的路径，A5 要求的「保留待判断」在改判后不可达。

裁定（**改代码，不是改契约**）：按当前状态换文案与行为，两条都要有。
| 状态 | 主按钮文案 | 行为 | 额外动作 |
| --- | --- | --- | --- |
| `progress=pending` 或 `cause_state=undecided` | 「保存错步，原因待判断」 | 发 `cause_state=undecided` | 「采纳选中原因并保存」（候选区内） |
| `cause_state=decided` | **「保存错步（沿用已判断原因）」** | 仍发 `cause_state=decided` + 原 `cause_code` | 「采纳选中原因并保存」（改判用）+ **「改为原因待判断」**（次级动作，发 `undecided` 并把旧原因推进 `cause_history`） |

- A3 原文要求的「提供『保存错步，原因待判断』」由 `undecided` 状态承担，不受影响。
- verify 必须断言：`decided` 下点主按钮 → 仍 `decided` 且 `cause_code` 不变；点「改为原因待判断」→ `undecided` 且 `cause_history` +1；`undecided` 下主按钮文案逐字为「保存错步，原因待判断」。

**R-06（low）｜空状态主按钮文案**

裁定（**准，回写契约**）：§4 的 A1 改为——**三种状态，主按钮各不相同，都不许 disabled**。
- `state=no_answers`：主按钮为 **「导入作答」**，可点击，直达导入路径；
- `state=has_pending`（`overview.next` 非空）：主按钮为 **「查看待核对作答」**，单击直达下一份；
- `state=all_checked`（`overview.next` 为空、`total>0`）：主按钮为 **「查看核对记录」**，直达 `#/class/{id}/check/records`；**不得**给一个空的「查看待核对作答」，也不得置灰；
- 全部状态都**不得 disabled**。理由：空班没有可核对的作答，「查看待核对作答」置灰等于没有下一步；而全部核对完时，老师真正想做的下一步是回看记录，不是再点一次已经不存在的「下一份」。这与 A1「区分『尚未导入作答』与『本次作答已核对完』」的意图一致。

> 补记（2026-11-24，T13 复审 N-03 提出）：本条最初只写了两种状态，实现里 `all_checked` 已按「查看核对记录」做了（`app.js` 无 `next` 分支），lead 认定实现更合理，故补写第三种态，契约与实现对齐，**不改代码**。

**R-07（low）｜全角减号下 `contrast.actual` 不是逐字原文**

事实：学生原文写 `3x－2=12`（全角 `－`）时，`hint_text='－2'`（正确），但 `contrast.actual='-2'`（被规范化成半角）。界面「学生这一行」因此显示学生没写过的写法，违反 §2.1 第 2 条。

裁定（补充 §2.1）：**`contrast.actual` 必须与 `hint_text` 逐字相等，且两者都逐字取自 `first_bad_text`；任何规范化只允许出现在 `contrast.expected` 一侧，且必须可被上一行原文解释。** 全角/数学减号 `－`、`﹣`、`−` 一律保留学生写法，不得替学生改成 `-`。案例 A 用半角输入时输出零变化（`hint_text='-2'`、`expected='3x-6'`、`underline={2,4}`）；用全角 `3x－2=12` 输入时 `actual` 必须是 `－2`。

### 5.3 演示批次隔离的实现方式（T6 起不再用触发器）

**合成数据不进真实作业/统计**靠三层**显式**机制，不靠任何「写入时悄悄改数据」的隐形行为：

1. **批次名不可撞**：`DEMO_BATCH = "【合成演示】不计入真实作业"`，真实导入不可能自然取到（§5.1 常量表在 `db.py`，`demo_answers` 再导出，触发器/迁移/seed/查询共用同一份字面量）。
2. **查询侧收口**：`answer_check` 的每条 check 查询（`queue_rows` / `_batch_counts` / `records` / `resolve_batch`）都按 `(batch, source)` 过滤；`stats.answer_check_stats` 另外显式 `AND a.source<>'合成演示'`（§3.6）。
3. **迁移期一次性归位**：`ensure_answers_schema()` 升级时把「`source=合成演示` 且 `record_key` 以 `DEMO-` 开头」的行挪回演示批次——只在升级时跑一次、有备份、可审计。**真实作答一条都不动**（没有 `DEMO-` 前缀）。

> **T6 删除的两个库级触发器**：`trg_answers_demo_batch_ins` / `trg_answers_demo_batch_upd` 曾把「写进真实批次的演示行」在 INSERT/UPDATE 后悄悄改成演示批次。删除理由有二：① 它们是隐形行为——某一行为什么换了作业，从数据上看不出来；② 它们若成为唯一防线，绕过触发器（或旧库还没建触发器）统计就会被演示数据污染。现在旧库打开时 `Database._ensure_columns()` 会显式 `DROP TRIGGER IF EXISTS`，新库根本不建。**删掉之后统计仍然干净**由 150 套件 17.0–17.7 锁死：故意把演示行直接写进真实批次，`expected` / 总览份数 / 队列都不变，显式查演示批次时 `expected` 恒为 0。
>
> 代价（如实登记）：如果有人**绕过应用**手工把演示行写进真实批次，界面不会再替他把行挪回去——它会在该批次里显示为一条「合成演示数据」的作答，但**仍不计入任何统计**，`reset`（§3.5）也仍按「三重条件」把它清掉。

## 8. 个体 AI 入口的账号级开关（R1-14）

### 8.1 口径

**默认不外发**。桌面端 6 个个体 AI 入口（错题重新分析、错题照片分析建议、个人辅导建议生成、追问候选生成、追问后的错因候选生成、作答分析）在「分析方式＝真实通道」时，默认一律返回 **403 `ai_isolation`**（文案与 R1-07 逐字相同）；只有该**教师账号**显式开启 `users.ai_individual_allowed` 之后才真调用。

这不是恢复 1.8.1 的无条件外发，三条约束同时成立才算「可外发」：

1. **客户端注入了 provider**——桌面端按账号设置构造；网页端 `server.py` 恒不注入（`ai_provider=None` → `MockProvider`），因此**网页端永远走不到真实通道**，也不显示这个开关；
2. **该教师账号显式开启**——`users.ai_individual_allowed`（默认 0）。开关只存在于库里，不读环境变量、不认「老师勾了同意」这类客户端布尔值；
3. **每次发送都过脱敏白名单 + 写审计**——见 §8.2 / §8.3。

### 8.2 脱敏白名单（发送前逐层判定，`src/app/vision.py`）

| 判定 | 覆盖 | 不允许出现 |
|---|---|---|
| `payload_field_error(body)` | 请求体顶层字段、`messages[]` 的 `role` / `content`、内容块类型、图片 URL/base64 大小 | 任何白名单外的键（`answer_id`、`student_id`、`class_id`、`account`、`username`、姓名…） |
| `job_field_error(job)` | `analyze()` 的作业字段 | 同上（`ALLOWED_JOB_FIELDS` 之外一律拒发） |

实测（`tests/verify_r1_14_account_ai.py` 3.4/3.5，桩服务收到的真实请求体）：

```
实际发送的请求体字段（3 条）：
[{"path": "/v1/chat/completions",
  "fields": ["messages[system,user]", "model", "temperature", "max_tokens"]}, …]
```

也就是说真正发出去的只有模型名、系统/用户两条消息、温度与 token 上限——**没有姓名、学号、班级名、answer_id、account**。审计里也只记这些**字段名**，不记取值（见 §8.3）。

### 8.3 外发审计（`ai_egress_audit`）

每次「真的要把请求发出去」之前写一行，写完才发送；**审计写失败就不发送**（`vision._note_egress` 在 `urlopen` 之前抛 `AnalysisError(code="audit")`）。

| 列 | 内容 |
|---|---|
| `user_id` / `username` | 谁（教师账号） |
| `flow` | 哪个入口（6 个流程名之一） |
| `model_channel` | 哪条通道：`<mode>/<service>`（如 `custom/本机桩`） |
| `payload_fields` | **字段名清单**（JSON 数组，如 `["messages[system,user]","model","temperature","max_tokens"]`），不含任何取值 |
| `payload_bytes` | 请求体字节数（体量可核，内容不落库） |
| `created_at` | 什么时候（本地时区 ISO-8601） |

**旧库兼容**：审计表与开关列都走既有套路——新库由 `SCHEMA` 直接建；旧库**缺列按「关」处理**（读不报错），第一次写开关时 `ensure_ai_switch_column()` 补列、第一次真实外发时 `ensure_ai_egress_audit()` 建表；两者都幂等。`REQUIRED_TABLES` 未改，桌面端只读完整性检查不会因为旧库没有这些结构而拒绝打开。

### 8.4 接口

| 方法/路径 | 说明 |
|---|---|
| `GET /api/account/ai-individual` | 读开关（网页/桌面都能读）。响应：`{"ok":true,"ai_individual_allowed":bool,"ai_individual_switch":"account","ai_egress_available":bool,"note":…}`；`ai_egress_available` 只在注入了 provider 的桌面端为 `true`，网页端恒 `false`（能改偏好、不能外发）。 |

### 8.5 与 R1-07 的关系

R1-07 的「默认不外发」原样保留：开关关闭时 6 个入口的返回与 R1-07 **逐字等价**（`tests/verify_r1_07_isolation.py` 73 项一条不少全绿）。R1-14 只是在这条规则上加了一个**显式的、账号级的、可审计的**放行条件，并且仍然只有一道闸门：

- api 侧 `_reject_individual_ai()`：判定账号开关，通过时把授权盖到**本次请求的 provider 实例**上；
- vision 侧 `egress_error()`：只认 `PURPOSE_TEACHER_INDIVIDUAL` + `provider.individual_allowed`；
- 模块侧（`tutor.generate` / `followup.suggest` / `followup.update_causes` / `answer_review.analyse`）不再各自重复拦截，而是读同一个授权位；没有授权时仍按原样 403/409。

授权不写全局变量、不落库到 provider 之外、不跨请求保留：下一个请求重新过账号开关。
