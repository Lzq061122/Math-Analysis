### 1.3 表结构（15 列）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | 自增主键 |
| `user_id` | INTEGER NOT NULL | 导出账号（`users.id`） |
| `class_id` | INTEGER NOT NULL | 所属班级 |
| `kind` | TEXT NOT NULL DEFAULT 'class' | `class` / `student` |
| `student_id` | INTEGER NOT NULL DEFAULT 0 | 个人报告的学生；**班级报告存 0**（不用 NULL，省掉三值判断） |
| `title` | TEXT NOT NULL DEFAULT '' | 导出时的报告标题**原样快照**（班级/学生改名不追溯） |
| `purpose` | TEXT NOT NULL DEFAULT '' | 导出用途 |
| `data_version` | TEXT NOT NULL DEFAULT '' | 导出时的数据版本串（历史事实，不用当前常量反推） |
| `scope` | TEXT NOT NULL DEFAULT '' | 筛选范围（JSON 串） |
| `batch` | TEXT NOT NULL DEFAULT '' | 批次 |
| `path` | TEXT NOT NULL DEFAULT '' | 保存路径 |
| `sha256` | TEXT NOT NULL DEFAULT '' | 导出文件校验值 |
| `bytes` | INTEGER NOT NULL DEFAULT 0 | 文件字节数 |
| `generated_at` | TEXT NOT NULL DEFAULT '' | 报告生成时间（快照时间，不是入库时间） |
| `created_at` | TEXT NOT NULL | 入库时间（排序键） |

索引：`idx_report_exports_user (user_id, created_at DESC)`、`idx_report_exports_class (class_id, kind)`。

> `title` 与 `data_version` 是 analytics 在 t9 验收前提出的两列（captain 已同意纳入最小集）：没有它们，`load_history` 只能靠 `classes.name` / 当前版本常量反推，等于让历史记录跟着后来的改名和升版漂移。

### 1.4 读写函数（只做插入与按账号倒序读）

```python
report_exports_ready(db) -> bool                      # 表是否存在（旧库读侧安全退化）
add_report_export(db, user_id, class_id, kind, student_id=0, purpose="", scope="",
                  batch="", path="", sha256="", bytes=0, generated_at="",
                  title="", data_version="", created_at=None) -> int   # 返回新行 id
list_report_exports(db, user_id, limit=50, class_id=None, kind=None) -> list[dict]
```

- `scope` 传 dict 会自动转 JSON 串（`sort_keys`，键序稳定）；传字符串原样存。
- `add_report_export` 在事务里先 `CREATE TABLE IF NOT EXISTS`（幂等，照 `ensure_ai_egress_audit` 既有做法）——老库在 captain 接线完成前也不会因为少一张表丢历史。
- `list_report_exports` 的 `user_id` **必填**：不提供「不传账号读全部」的入口，避免调用方一不留神跨账号读出别人的导出记录（10.9 断言）；同账号内可用 `class_id` / `kind` 过滤（10.10）。
- **上限由调用方决定**：`limit` 只限制读取条数，db 层不删任何行（10.11 断言：读 1 条后表里仍 3 行）。派单要求留痕 ≥ 六个月，db 层静默截断就等于数据丢失。
- **不做业务判断**：不校验 `kind` 取值、不检查班级归属、不校验路径——那些属 `report_pdf` / api。
