## 1. 实现内容与入口

| 函数 | 变化 |
|---|---|
| `save_history(db_file, entry)` | 签名不变。内部按 `db_file` 打开 `Database`，调 `db.add_report_export(...)` 写 `r2_report_exports`；返回**该账号**最新历史列表（界面直接拿去重画）。写入前先做一次侧车迁移；写完在**写入侧**把该账号裁到 50 条 |
| `load_history(db_file, user_id=None, limit=50)` | 签名向后兼容（新增两个有默认值的关键字）。`user_id` 给定 → 只读该账号（账号隔离）；不传 → 整表读取（与旧侧车行为一致，不倒退）；表还没建（老库未迁移）→ 退回读侧车 JSON，升级路径上历史不丢。返回条目的键与旧版**逐字段一致**（`at/kind/title/purpose/filters/batch/path/bytes/sha256/user/data_version`，另附 `user_id/class_id/student_id/id/created_at`） |
| `history_path(db_file)` | 保留函数与返回值（库同目录的 `r2_report_exports.json`），但**不再作为写入目标**，只作兼容与旧数据迁移定位；docstring 已写明 |
| `import_sidecar_history(db_file)` | 新增：把旧侧车 JSON 一次性搬进表，**按账号做闸门**（该账号在表里已有行就整批跳过，防「搬到一半崩了再搬一次翻倍」），成功后把文件改名 `.imported`（不删，留证据） |
| `export_pdf(...)` | `entry` 增加 `user_id/class_id/student_id`（入库定位用；`class_id` 在备份恢复时会重映射，报告内容本身不受影响） |
| 内部 `_trim_history()` | **写入侧**裁剪：只删该账号超出 50 条的最旧行；db 层不删数据（`limit` 只限读取） |

要点：
- **字段口径**：`title`/`data_version` 写「导出那一刻的值」（改名/升版不改写历史），`user` 由读时 join `users.username` 补回（db 层不做 join，保持只读函数最小）。
- **幂等**：同一份报告连续导出两次 = 两条独立记录（不去重；路径不同就是不同导出）。
- **不做「读一下就偷偷写库」**：迁移只在写入路径发生。

### 新增断言（第十组，10.1–10.22）

1. **字段**：两次导出后有两条独立记录、最新在前；`at/kind/title/purpose/filters/batch/path/bytes/sha256/user/data_version` 与导出记录逐字段相等；`user` 从 `users` 表补回；表里 2 行且侧车文件不存在。
2. **账号隔离**：账号 1 只读到自己 2 条、账号 2 只读到自己 1 条、不传账号时整表读取（旧行为不倒退）。
3. **备份恢复（本任务存在的理由）**：`create_backup` → manifest 里带条数 → `inspect_backup` `same_key=True` → `apply_staged(mode="restore")` 到「同账号空库」→ `load_history` 仍读到 2 条，`title/kind/filters/sha256/path` 完好，`class_id` 已重映射，别的账号的历史不会算进本账号。
4. **上限**：连续 55 次导出 → 表里 50 行、读回 50 条、最旧 5 条被裁；`limit=5` 只限读取、表里仍 50 行。
5. **侧车迁移**：旧 JSON 一次性搬进表（1 条）、文件改名 `.imported` 留证据、字段与旧 JSON 一致、**再次调用不重复导入**（返回 0、表里仍 1 条）。
