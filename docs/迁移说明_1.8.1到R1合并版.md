## 九、维护者附录：几个「为什么这么实现」的口径

1. **演示批次常量放在 src/app/db.py**：DEMO_SOURCE / DEMO_BATCH / DEMO_RECORD_PREFIX 定义在数据层（db.py:280 附近），demo_answers 再导出同一份字面量。理由：迁移（ensure_answers_schema 的一次性归位）、演示 seed/reset、以及所有查询侧的 (batch, source) 收口都要用同一个字面量；放在一处才不会出现「迁移认一个批名、查询认另一个」的分裂。批名判定用**显式名单成员判定**（demo_answers.is_demo_batch），不用前缀猜——批名是老师在 CSV 里自由填的。
2. **两个「写入时自动改数据」的库级触发器已移除**：它们会把写进真实批次的演示行悄悄改成演示批次，属于隐形行为。现在改为「迁移期一次性归位（有备份、可审计）+ 查询侧显式过滤」，演示数据不进真实作业/统计由查询保证；旧库打开时显式 DROP TRIGGER IF EXISTS 清掉残留。误伤回滚：用升级时留下的 pp.db.bak-* 覆盖回去即可。
3. **1.7.x 旧库的升级路径**：先建表 → 补列 → 回填历史来源 → 合并重复行 → 最后建索引。旧版本在这里曾抛 MigrationError: no such table: answer_followups（因为先补列而后建表），现已修复，并有反向自证：把顺序改回去，同一份旧库必须重新报错。
4. **备份与恢复范围**：新增的 i_egress_audit（外发审计）也进备份/恢复；恢复按账号替换、缺表不清空、失败整体回滚。
